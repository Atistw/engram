# 調研方法

照順序做，每節產出對應備忘錄一節。

## 1. 來源順序
一手原始碼與 README > 論文 > 作者文件 > 第三方摘要。原始碼 clone 到知識庫外，記 commit 與日期。引用一律 `檔:行`。第三方摘要與論文裡的成效數字，沒自己重現前標「未驗證」。

## 2. 找出核心引擎
引擎 = 拿掉它，成果就不能再歸功於這個框架的那個部件。三條線索：
- 程式把預算花在哪（迴圈、重跑次數、呼叫配額）。
- 作者自己的消融實驗或「沒有它會怎樣」的描述。
- 把名字去掉看剩什麼：只剩「讀資料寫建議」，那就不是這個框架。

寫下：引擎是什麼、在哪個檔哪幾行、它依賴什麼條件（標準答案、可重跑的任務、大量樣本、自動評分）。

## 3. 環境假設對照
列兩欄：框架假設的環境 / 使用者的環境。你的環境常見固定項：單人、知識庫與對話為主、修正來自使用者糾正模型（強訊號）、樣本少、無自動評分；作業系統與同步方式依實際填。引擎依賴的條件在使用者這邊不成立，就標「引擎不可移植」。

## 4. 借／改編／不借
一表三欄，每列附理由與 `檔:行`。每一列可用一句話判斷：拿來後使用者少做什麼、或少錯什麼。

## 5. 命名誠實
引擎沒有帶過來，備忘錄與後續文件寫「受 X 啟發的 …」，不寫「X」，也不寫「借鏡自 X」。

## 6. 基線
寫出最便宜的做法：主 session 直接對同一份輸入做同一件事。估 token，標「估」或「量」。提議版本必須指出在哪個維度贏過基線（成本、品質、可重複），贏不了就建議不做。

## 7. 重疊掃描
在 `CLAUDE.md`、已知陷阱、`_skills/`、hook、mod、TASKS 搜同功能。列出重複與衝突（例如既有的派工或驗收規則）。新增常駐文字必須同案指出刪哪一句。

## 8. 驗證計畫
寫明：誰訂標準答案、誰判分（不得與建置者同一 session）；有沒有對照組；用哪份真實資料；樣本數與它能支持的結論；什麼結果代表停手。量測的指標必須就是立題時的有效判準（量核可率不等於量事故是否下降）。實跑的占比拆開看子群，避免健康樣本與問題樣本混在一個數字裡。

## 9. 覆蓋行
一行列出：讀過哪些、沒讀哪些；跑過哪些、沒跑哪些。

## 10. 預算
立題時的預算上限。接近上限就停手回報，由使用者決定加碼或收手。
